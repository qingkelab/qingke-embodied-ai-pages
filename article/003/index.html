不更新模型参数，机器人也能在部署现场调整行为吗？——RoboICL 技术解读

开场：机器人也开始做 ICL 了？

语言模型有一个用了很多年的接口：把几个例子放进上下文，模型就按例子的模式回答，不用改任何一个参数。机器人领域长期缺少一个像 LLM ICL 那样成熟、统一的对应接口——已有的相关工作（RICL、GEN-1.5、Zero-WAM 等）各自解决了一部分问题，但还没有形成同一种部署时接口。想让一台机械臂做一件新的事，常规做法仍然是采数据、标注、微调、部署，出问题再回来采一轮。

过去几年，机器人适配基本都发生在参数里：把新数据喂进训练流程，改完权重再上机。RoboICL 试的是把其中一部分适配搬进上下文——同样的模型，换一批输入，行为随之改变。

RoboICL 想试的是另一条路。它让通用多模态模型 GPT-6 Astra 在推理时（inference-time）看着几条示范直接给出动作，整个过程中不更新模型参数。做法是把示范轨迹和部署时的交互记录用同一种格式呈现，模型通过单个 Act 工具输出双臂末端动作序列，一个确定性的 harness 负责校验与执行。

先说清楚边界：截至 2026-09-19 的本轮核验，未发现 RoboICL 对应的 arXiv 条目。 当前可核的一手材料是项目页、代码仓库和作者发布的 released request artifact。它目前报告的全部量化结果都在仿真里，没有正式的真机量化结果。本文讨论的是这套设计值不值得关注，而不是它已经解决了什么。

这篇文章想回答三件事：RoboICL 到底改了系统的哪一层；它的证据能支撑到哪一级；以及为什么「示范能不能帮上忙」这个问题，在另一份官方报告里得到了方向相反的结论。

还需要约定一件事：本文说的「接口」「主线」都是问题层面的说法，不是模型谱系。同一条技术线上真正连续的东西是问题——适配发生在哪里、用什么单位发生、代价由谁承担；具体系统之间更多是共享问题、各自取法。

一、机器人为什么也需要 ICL？

先解释问题本身。机器人策略的部署逻辑，和语言模型很不一样：模型的适配能力通常被写进参数里，部署之后就是一个固定函数。

传统流程把「学会」和「使用」切成两段。训练阶段决定策略行为，部署阶段只负责执行。这种切法在任务稳定时很高效，代价是任何现场变化都得回到训练环节处理：换一个初始位置、换一种摆放、换一个任务顺序，标准动作是补一批数据再训一次。工程师当然可以用示教复现、脚本、状态机绕开一部分，但这些绕法本身也是提前写好的。

把这件事说成「参数更新的成本高」还不够准确。参数路径更深的问题是：它把适配的单位设成了「模型」，而部署现场需要适配的单位常常是「这一次」。 工位变了、料箱位置变了、任务顺序变了，需要调整的可能只是当前这个回合的几十步决策，但参数路径要求你为此重训一个模型、再走一遍验证。适配粒度与需求粒度不匹配，是这条路径的结构性摩擦。

这里有一个容易被忽略的事实：推理时能改变的，不只是模型权重。 上下文里放什么、系统保留哪些历史、回合之间如何传递反馈，同样会改变下一步动作。语言模型把这条路径用到了极致；机器人领域长期默认走参数那条路，很大程度上是因为动作的反馈回路更贵——你得真的动一下，才知道对不对。

RoboICL 的出发点就是这个空位。它要回答的问题是：如果不更新模型参数，机器人能否利用少量 execution-grounded demonstrations，在 inference-time 针对当前任务与新场景调整闭环行为？

这句话里有两个词要单独限定，否则很容易被读大。

一个是 inference-time：示范在部署时进入决策，不是先训进去再用。另一个是 execution-grounded：示范记录的是机器实际执行的过程，而不是一段理想轨迹。

这里要先堵一个常见误读：「不更新模型参数」说的是当前这个适配阶段，不是说这套系统没有训练过。 基座模型本身当然是训练出来的；RoboICL 改变的是部署时怎么使用它——不在当前任务上更新策略参数，而不是「整个项目从不训练模型」。本文后面所有「不更新参数」都按这个含义读。

还有一个范围问题必须提前讲明。下面这两个说法不是同一件事，评测强度差了很远：

  • 同一个任务、同一个能力，在给定条件下把行为调得更稳（task-conditioned behavior adaptation）；
  • 换一个模型从没见过的任务类别，让它在部署现场学会（cross-task generalization）。

本文把这类主张拆成五级（L1 到 L5）：L1 是推理时用示范且不更新参数；L2 是任务内的行为适配；L3 是新布局、新初始状态的泛化；L4 是跨任务类别；L5 是跨本体。RoboICL 当前的量化证据主要覆盖 L2–3；L4、L5 不是它的实验结论。 后文每次给数字都会标明它落在哪一级。

把这条阶梯写出来，是因为「机器人在部署现场学习」在传播里几乎总被当成一件事。实际上 L2 与 L4 的难度差着量级：前者只需要在当前任务的条件分布内调整行为，后者要求模型把从未见过的任务意图从上下文里读出来。这两件事能用的证据也不一样——前者可以用同一任务的示范对照，后者必须换任务重新评测。

图 1：左边是常规做法——示范进入梯度更新，改变的是参数；右边是 RoboICL 的做法——示范进入上下文，改变的是这一次推理的输入。两条路的「学习位置」不同，不是同一条路的新旧版本。图：青稞社区绘制。

二、传统 VLA 的隐含限制

把问题放到 VLA 语境里会更清楚。这里要避免一个常见误读：这不是说传统 VLA 不能泛化。

多任务、跨本体的 VLA 在训练分布内的泛化已经相当可观。真正的限制在别处：传统训练范式把适配写进参数，而不是写进 inference-time context。 参数一旦固定，模型对新场景的适应就只能在两种方式里选——要么靠训练时覆盖到，要么靠外部的重试与人工干预。

这件事在 2025 年的一篇工作里被写得很直白。RICL（Adding In-Context Adaptability to Pre-Trained Vision-Language-Action Models）的摘要指出：用模仿学习目标预训练的 VLA 不会自然获得 in-context learning 能力。 它的解法是先做一次有针对性的重训，把 ICL 能力注入模型，之后用户提供 10–20 条新任务示范，系统把其中相关片段取回上下文，从而在不更新参数的情况下执行新任务；论文报告在多个新操作任务上、每任务 20 条示范的条件下取得 in-context 提升。

这条信息有价值，因为它把「机器人为什么不会 ICL」从直觉变成了可引用的事实：ICL 不是把模型做大就自动冒出来的能力，它是一个需要专门接入的接口。

另一篇工作把同一件事的说法讲得更直白。Zero-WAM 的摘要把 in-context learning 的作用描述成「把泛化变成任务指定问题」——模型不需要为目标任务改参数，只需要知道这一回合要做什么。这句话点出了两种路径的分界：参数路径里，「泛化」要求训练分布覆盖到；上下文路径里，「泛化」先变成「任务怎么被指定」的接口问题。

顺便把术语边界画出来。本文说的 robot ICL，至少同时满足三条：一，推理时使用示范；二，示范确实能改变当前行为；三，示范与部署决策共享可对应的 interaction grammar——两条轨迹的观测、动作、反馈结构能互相对齐。

第三条是关键。它把 RoboICL 与「把一条轨迹塞进 prompt」区分开：重点不是上下文里多了几条轨迹，而是示范本身被定义成了与 deployment 同构的闭环交互记录。

三、RoboICL：让 GPT-6 Astra 直接进入 robot policy loop

RoboICL 的系统结构可以直接从作者发布的 request artifact 里读出来——这份 artifact 是一次 2-shot「Put bottles in a bin」回合的完整序列化模型请求，已逐字段核对过。

动作只有一个来源：GPT-6 Astra。 artifact 显示，整个请求只注册了一个工具 act，tool_choice 强制选择它，parallel_tool_calls 为 false。换句话说，每个回合恰好一次调用，没有 VLA 提议、没有额外 agent runtime、没有 skill library 兜底。模型名是 gpt-6-astra-ssvip，reasoning effort 设为 xhigh。

为什么「只有一个工具」这件事重要？因为工具面决定了动作从哪来。如果一个系统里既有 VLA 提议、又有技能库兜底、还有 agent 负责挑选，那么最终分数里有多少来自基座模型的闭环理解、多少来自外挂模块，就很难分开。把工具面压缩到单个 act，换来的是归因清晰：这一步动作由谁产生，没有歧义。

动作接口是一个固定形状的矩阵。 act 的参数 schema 要求 actions 恰好 15 行 × 14 列，另有一个不超过 400 字符的 execution_note。14 列对应双臂各自 6 自由度末端增量加一个夹爪，artifact 的指令原文写明 EE means link6, not fingertip/TCP——末端点定义在第 6 关节，不是指尖或工具中心。

执行的是一条确定性流水线。指令规定命令以 25 Hz 运行，单步平移范数不超过 0.03 米、旋转范数不超过 0.15 弧度。关节变化超过 0.15 弧度的逆解会被拒绝，这一条带来的连锁后果值得注意：被拒之后该动作不会执行，剩余的动作块会被丢弃，所以要靠回执区分「已经执行的前缀」与「被丢弃的后缀」。

「确定性」这个词要解释清楚，否则容易被读成「harness 也在做决策」。它只做四件事：校验调用是否符合 schema、把超界的目标裁剪回边界内、求解逆运动学、把解出来的关节轨迹按 25 Hz 播放。策略完全由模型决定；harness 决定的只是「哪些动作能被物理执行」。 这条边界在阅读结果时很重要——执行层面出的问题属于系统问题，不能当成模型判断的对错。

观测是三路 RGB 加本体状态。输入是 1920×480 的三视图（左腕、头部、右腕各 640×480）。这里有一处容易被写错的边界：harness 会把头部相机的内参 K、外参 T 以及像素投影公式一并交给模型。被隔离的是评测器派生信号，不是全部环境几何——所以不能写成「模型只看 RGB 图像」。

上下文本身也值得看一眼。artifact 里这次请求的 input 共 81 项：29 组「文本 + 图」、15 次 function_call、15 条对应的 function_call_output、15 段纯文本、6 段 reasoning，外加 1 组锚点内容。这个构成说明上下文里装的不是几条轨迹，而是一段带反馈的交互历史——调用、回执、推理记录和观测交替出现。

评测信号确实被隔离了，但有一处例外。 指令原文写着 Do not access simulator object poses, rewards, task code or layouts.；当前回合回执里的 success 字段值不是布尔，而是一句占位字符串 not supplied to policy; infer progress from RGB only；训练侧回执的 success 与 terminal 都是 None；result_state 只包含机器人自身的关节与末端状态，没有任何物体位姿。保留下来的评测器派生信号只有 terminal，也就是项目页所说的 continuation flag。准确表述是「评测信号被隔离」，不是「完全没有 evaluator signal」。

四、真正关键的设计：execution-grounded demonstration

这一节是全文的技术重心。项目页把整套系统的信息流写成一条链：

observation → Act 调用 → 执行反馈 → 下一个 observation

这不是把示范轨迹贴进 prompt，而是让示范和部署共用同一套 interaction grammar。 部署回合里发生的事——模型看到观测、发出动作、拿到执行结果、再看到新观测——在示范里以同一种结构被记录下来。模型要做的决定，与它在示范里看到的决定是同构的。

具体到字段层面，回执里能读到的东西相当细：executed_step_interval（实际执行了预测中的哪一段）、predicted_steps 与 dispatched_steps、executed_steps 与 unexecuted_steps、executed_command_ledger_sha256、latest_tracking、controller_events，以及 terminal。

这组字段解释了为什么「执行过」这个信息重要：

  • executed prefix：模型知道 15 步预测里前几步真的落地了；
  • unexecuted suffix：模型知道剩下的动作因为逆解拒绝或其他原因没有执行；
  • controller events：中断、拒绝这类事件会出现在记录里，而不是被悄悄抹平；
  • tracking：命令与跟踪结果之间的差距可见；
  • terminal：回合是否继续属于可见状态。

这组字段还有一个更实际的作用：它让模型有可能把结果归因到正确的动作上。如果 15 步预测里只有前 6 步执行、后面因为逆解被拒，而回执只报一个整体结果，模型无法判断是哪一段出了问题。字段级记录把这层归因能力交还给了模型，这也是「闭环交互记录」与「一段带结果的轨迹」的差别所在。

图 2：示范（TRAIN）与部署（LIVE）走的是同一条 grammar：观测 → Act → 已执行前缀 / 执行反馈 → 下一个观测。这正是它与「把理想轨迹塞进上下文」的分界。图：青稞社区绘制。

如果示范只是一条理想轨迹，模型看到的是「应该发生什么」；在 execution-grounded 的形式下，模型看到的是「实际发生了什么、哪一段被打断、系统怎么回应」。后者与它下一步要做的决定处在同一个信息层面上。

必须补一句限定：「execution-grounded 比理想轨迹更有效」这一点并没有被实验单独拆开。 项目页没有提供「换成理想轨迹后性能如何」的对照。这条判断目前是机制层面的合理推断，不是已被隔离的因果关系。

五、长任务怎么记：bounded anchored LIVE memory

回合一长，上下文就装不下全部历史。RoboICL 的做法是把记忆本身当成一个 inference-time 系统设计问题。

项目页给出的策略是有界锚定：保留最初的完整交互块，之后按计划在若干位置保留锚点（项目页示例给出的位置是 0 · 140 · 280 · 420），最新的完整块与当前观测常驻。

锚点不是随手挑的，项目页给了选择规则：初始块一定保留，其余锚点目标在整个 episode 的时程上均匀调度；对每个目标，取第一个满足「起始 < 目标 ≤ 结束」的已完成执行块作为固定锚点。两个锚点之间，<TRAJECTORY_GAP> 的右端点随执行不断前移；当某个完整块跨过下一个目标，它就成为新的锚点。落在非锚点区间的完整观测与动作数组会被替换成显式的 gap 记录。

把记忆当接口来设计，本质上要回答三个问题：哪些过去必须常驻、哪些可以压缩成锚点、哪些必须显式声明为「已省略」。这三个问题没有标准答案，只有与任务时程和上下文预算相匹配的答案。 项目页给出的是一组具体参数，不是一套通用配方——这也是它属于系统设计、而不属于模型能力的原因。

被省略的部分不是悄悄消失，而是显式声明。 在 request artifact 里可以数到 13 处 <TRAJECTORY_GAP> 标记与 30 处 OBSERVATION_END。这个设计针对的是一种具体失败：如果省略不留痕，模型可能把两段不相邻的历史读成连续运动。

两条训练参考轨迹各贡献 5 个动作块，对应 2-shot 的示范规模。也就是说，被保留的既有示范、也有部署过程本身——部署回合的执行反馈同样会回来影响后面的决定。

「最新块 + 当前观测常驻」这一条也值得留意。它保证模型总能拿到最近发生的事和此刻的观测，所以锚点再稀疏，当前决策也不会失去上下文。这套记忆策略的目标不是「记住更多」，而是「在有限预算下保证当前决策有据可依」。

图 3：完整轨迹被压成「首块 + 锚点 + 显式 gap + 最新块 + 当前观测」。记忆策略本身就是推理时设计的一部分。图：青稞社区绘制。

不过作者没有对 anchor 策略做 ablation：没有「换成滑动窗口」「换成摘要」「不标 gap」的对照。所以这里只能说它是一种把记忆当接口来设计的实现，不能说它已被证明优于其他记忆方案。

六、3 个 demonstration 到底带来了什么？

项目页报告的第一组量化结果，是比较不同示范数量下的任务表现。

设置是两个任务、每个任务五个固定布局，条件为 0-shot、1-shot、3-shot。项目页报告的均值任务分（mean task score）变化是：

  • Put bottles in a bin：0.34 → 0.88
  • Build Tower：0.04 → 0.82

三个条件都必须一起写出来，否则这组数字会被读大：

  • population 很小：两个任务，每个任务五个固定布局；
  • 指标是均值任务分，不是 success rate，两个数不能互换口径；
  • 三条示范是同一任务的 task-conditioned demonstrations，示范与评测任务一致。

最后一条尤其重要。这不是 cross-task 的「学会新任务」，而是同一任务在给定条件下被示范调稳。 按第一节的分级，这组结果落在 L2 到 L3 之间。

三条示范怎么来的，项目页也写清了：每个任务从官方 TRAIN 划分里预先固定三条轨迹，挑选过程不接触测试布局的结果；每条轨迹抽 5 段互不重叠的 15 步片段，覆盖不同操纵阶段，包含初始观测，最后一段对齐轨迹终点；示范动作不做裁剪、插值或人工修正。三条示范合计提供 30 组固定三视角观测。

0-shot 那一列的含义也需要读准。它不是「没有条件」——模型仍然拿到语言指令、视觉观测和完整的 harness，缺的只是示范。所以这组数字衡量的是「示范这一项输入带来了多少变化」，而不是「模型有没有能力做这件事」。这也解释了为什么三条示范能把分数从 0.04 抬到 0.82：模型缺的是稳定发挥，不是任务理解。

但同一批能力背后还有一组方向相反的公开实验，读这组结果时必须一起看。RoboDojo 官方报告（Sep 16, 2026，RoboDojo Team）在 340 个匹配的 task-layout 组合（34 个任务、每任务 10 个布局）上注入单条示范，结果反而低于 zero-shot——zero-shot 是 78/340 = 22.9%，图像加末端示范是 61/340 = 17.9%，文本示范是 44/340 = 12.9%。报告的结论是：对能力已经足够强的基座模型，跨布局的单条示范既不补任务意图，也不提精度，反而可能把模型带偏。

两组结果方向相反，但不是同一设置：一个是 1-shot、示范来自不同布局；一个是 3-shot、示范来自同一任务。它们的正确用法是并置，说明「示范注入的效果高度依赖协议」——既不能用 RoboDojo 的结果否定 RoboICL，也不能用 RoboICL 的结果反驳 RoboDojo。

七、50-layout 结果应该怎么读？

示范数量之外，项目页还给了另一组口径不同的结果：把同一个任务铺开到更多初始条件下，看这套做法是否仍然站得住。

这组实验是在 Build Tower 上扫 50 个布局，seed 0。项目页报告：RoboICL 3-shot 的均值是 59.80，在图中列出的比较条目里排第 4；同为图中条目的 GPT-6 Astra Direct 是 16.40，排第 20。

这组数字比上一组更难读，有四点：

布局数从 5 放大到 50，覆盖的初始条件分布更宽；代价是单 seed——扩大布局与重复 seed 之间显然做了取舍，图上也把 RoboICL 的数值标注为 estimate。

  1. 它是一次单 seed 扫描，RoboICL 的数值在图中被标注为 estimate；
  2. 「第 4」是这张图里列出的比较条目的位置，不是整个 RoboDojo 榜的排名——这两件事不一样，写成「RoboDojo 排名第 4」是错的；
  3. 同一张图里还有更高的官方基线，最高到 82.93（GalaxeaVLA G0.5），所以正确表述是「在这个协议下达到了中上位置」，而不是「超过了专用 VLA」；
  4. 同一个任务名，在不同协议下不是同一个数字。

第 4 点最容易被顺手写错。RoboDojo 官方报告在官方协议（42 项仿真任务、每任务 50 个 episode、共 2100 次试验）下给出的是：GPT-6 Astra 的均分 28.97、成功率 22.48%，其中 build_tower 一项是 Astra 2.0 对 G0.5 78.7。而 RoboICL 项目页那张 Build Tower 图里的「GPT-6 Astra Direct 16.40」是另一个协议下的数字（50 布局、seed 0、图内比较项）。28.97、22.48%、16.40 这三个数放在同一句话里比较，是错的。 RoboDojo 官方报告自己就写着：不遵循官方 50-episode 协议的数字不具可比性。

还有一点对理解 RoboICL 有用：项目页的九任务表给出均值 57.33 对 36.11，作者自己标注这是 cross-protocol 的上下文，不是因果比较。这张表只能回答「哪些任务类型受益」，不能回答「谁比谁强」。

这张表的构成同样值得写出来，否则读者看不出它的样本是什么。评测设置是 eval_seed=0，九个任务各取五组确定性设置，合计 45 次 rollout；其中六个任务用标准布局 0–4，Arrange the largest number、Pack objects into a box、Fold clothes 三项用两组标准布局加三组随机布局。Classify Objects by Language 被排除，原因是它的官方 TRAIN 划分里没有该任务的专属参考轨迹。 逐任务看，RoboICL 在九项里有六项高于项目页所引的 GPT-6 Astra Direct 结果、两项更低、一项持平。评测案例与公开的 GPT-as-Policy 报告及其机器可读 data.json 对齐，得分由 RoboDojo 原生评估器给出。

定量结果之外还有两组定性案例，项目页把它们写成两条待验证的假设，而不是结论。

一组是精度：Fasten Screws（拧螺丝）要求毫米级对齐与可控插入深度，容错空间很小。同布局对照里，零样本 rollout 得 0.20，3-shot 完整完成、得 1.00。项目页描述的成功 rollout 有明确分步：先把黄色、白色螺母对准对应螺钉，用多轮短促顺时针旋转推进，中间夹着短暂的松开-重抓重置；红色螺母放到后面处理，出现故障后还做了恢复。对照之下，零样本基线大部分时间在寻找一个稳定的抓取位置。

另一组是策略自适应。Fill Pen Holder（装填笔筒）的三份示范给出两套手部分工：episode 0 是左手持笔筒、右手插笔，episode 96 与 99 反过来。测试 rollout 先采用后一种分工，临近结束时把笔筒交到左夹爪、建立新抓取后松开右手夹爪，在空中完成换手。示范里只有两套分工，没有这个过渡动作，所以项目页把它读成对已示范行为的重组，而不是复刻其中一套策略。整个过程中笔筒保持竖直、笔没有掉落。这次 rollout 在第 802 步因策略服务故障中断，没有记录官方结果，因此它只是 rollout 内部的定性观察，不能当作分数。

八、与 RICL / GPT-Policy / GPT-as-Policy 的差别

前两节都在读 RoboICL 自己的数字。要判断它在技术图上处于什么位置，还需要把它和同期几条路线并排看——但比的应该是接口，不是名次。

这张表要横着读，不要竖着排名。每一列回答一个不同的问题：是否更新参数，决定适配成本落在哪里；demonstration 一列，决定上下文里放什么；action source 决定谁在产生动作；live feedback 决定系统能不能从执行结果里纠正；memory 决定上下文预算怎么花。任何单独一列都不构成「谁更好」的依据。

| 方法 | 基础模型 | 是否更新参数 | demonstration | action source | live feedback | memory |

|------|----------|--------------|---------------|---------------|---------------|--------|

| RoboICL | GPT-6 Astra | 不更新 | execution-grounded（观测 → Act → 回执 → 下一观测） | 通用多模态模型直接生成 15×14 双臂末端增量 | 有（已执行前缀 / 丢弃后缀 / 中断 / tracking） | 有界锚定 + 显式 gap |

| GPT-Policy | VLM agent | 不更新 | context compiler 保留任务相关视觉转移 | VLM 提议 robot-tool 动作，受限控制器验证并执行 | 有（工具结果与观测在线返回） | rolling context window |

| GPT-as-Policy | π0.5 + GPT-6 Astra | 不更新 | 混合 | π0.5 提议动作，GPT-6 Astra 审查并可修正 | 有 | 运行上下文 |

| RICL | 预训练 VLA | 先 finetune 注入 ICL，之后不更新 | 检索到的目标任务示范（10–20 条） | VLA 自身 | 有 | 取回的示范 |

| Zero-WAM | video-action 模型 | 训练后不更新 | 人类视频作为任务指定 | 视频-动作模型 | — | context 中的人类视频 |

图 4：只比较接口，不比较优劣。三条路线都在推理时利用上下文，但动作由谁产生、上下文里放什么、反馈怎么回来，各不相同。图：青稞社区绘制。

先分清两个容易被混为一谈的名字。 GPT-Policy 是 arXiv 2609.19138（In-Context Robot Learning with VLM Agents），由 context compiler、VLM 提议的 robot-tool 动作、以及验证并执行动作的受限控制器组成，论文报告在真机试验中人类视频示范能在没有机器人动作标签的情况下提升任务完成度。GPT-as-Policy 是另一项独立工作，测的是 π0.5 提议加 GPT-6 Astra 审查/修正的混合系统。两者是两项独立工作，不能互相代替。

GPT-as-Policy 的公开材料说明了一件事：评测口径本身需要读清。 它的 README 与 provenance 文件写明：Direct 的 26% 成功率与 37.81 均分，后者只基于 48 个有 native score 的 episode；hybrid 是 48% 与 62.60；GPT 修正发生在 14.4% 的已执行控制步上；十个任务每个五个对齐 case；而它引用的官方模型对照是按所选任务与场景构成重新加权的公开参考，不是同 seed 重跑。这组数字可以作为邻近评测背景，但不能用来证明 RoboICL 的因果收益。

这类系统还有一个共同风险：一旦评测器派生的字段（成功标记、奖励、场景元数据）出现在模型能看到的地方，分数就不再只是能力的函数。所以在读写这些报告时，先确认「模型这一侧能看到什么」比先看分数更有用。

RICL 与 RoboICL 的差别在「为 ICL 付了什么代价」。 RICL 承认 VLA 不天然具备 ICL，于是先花一次重训把能力注进去；RoboICL 直接使用未针对机器人微调的通用模型，适配成本落在上下文与系统设计上。两条路都在避免目标任务上的参数更新，但一个是「先注入再适配」，一个是「直接用通用模型」。

Zero-WAM 换掉的是上下文的模态。 它用人类视频作为任务指定——论文报告构造了 8.6K 个任务上的 74.2K 人类-机器人 ICL 对，并报告在 RoboTwin 2.0 的七项未见任务上平均成功率 47.0%。这提示上下文里放什么并不是单选题：轨迹、视频、文本都可能是任务指定的载体。

把这些路线摆在一起，可以看出它们各自选择在哪一层承担适配成本：RICL 选择「注入一次、之后复用」；RoboICL 探索直接用通用模型的闭环理解；GPT-Policy 采用工具化的动作提议以换取可控性；GPT-as-Policy 采用「已有 VLA 提议 + 通用模型审查」的分工；Zero-WAM 选择用人类视频作为任务指定。这些都是接口层面的取法差异，目前没有任何一份证据能说明其中哪一条是终点。

九、它真正意味着什么？

编辑部判断：如果这条路径成立，机器人学习可能不只发生在参数空间，也可以发生在上下文空间。 这不是领域已经形成的共识，只是把 RoboICL 的设计放进更长的技术线之后，我们看到的接口变化。

更精确的说法是「接口扩展」。VLA 这条线长期在回答「动作怎么学」；RoboICL 这类工作把问题挪到「部署时怎么继续调整」。两者不是替代关系：参数仍然是能力底座（基座模型本身就是训练出来的），上下文决定这一次怎么用它——改变的是当前适配阶段，不是「这套系统没有训练过」。

它把三个原本分散的设计问题拉到一起：

  • action interface：动作以什么形状、什么频率进入系统；
  • memory policy：长回合里哪些过去可见、哪些被显式省略；
  • feedback loop：执行结果如何回到决策里。

这三件事在传统流程里分别属于数据、工程与控制器，现在成了同一个推理时设计问题。 这是本文认为它值得关注的原因，而不是某一个分数。

还有一个更长期的观察。当一个接口从「参数」扩展到「上下文」，评价方式也必须跟着变。 现在的 benchmark 大多在测「固定策略在给定任务上的能力」；如果一个策略的表现取决于部署时给了什么示范、系统保留了哪些历史，那么同一次评测的结果就不再只是模型的属性，而是一整套系统配置的属性。到那时，「这个模型多强」这个问题本身就会变得不好回答。

这也是本文反复强调「数字要连协议一起写」的原因。RoboICL 与 RoboDojo 官方报告在同一件事上给出方向相反的结论，恰好说明：在这个阶段，协议差异对结论的影响可能大于方法差异。这不是谁做错了，而是这类系统还没有形成统一的评测口径。

十、它还没有证明什么？

下面十二条是写这篇稿子的前提，缺一条都会把结论写大。

这十二条不是免责声明，而是阅读顺序：先确认结果在哪个环境里，再确认样本量、seed 与协议，最后才看数字。任何一条被跳过，结论都会比证据大一圈。

  1. 全部量化结果在仿真（RoboDojo）里，没有正式的真机量化结果。补充背景：RoboDojo 官方报告其实尝试过真机，但未跑完官方 18 任务协议——报告称 Astra 在真机试验中反复给出物理上不合理或不安全的动作，包括损坏硬件的事故，因此停止测试，保留的 12 任务 / 33 次试验只作诊断证据。
  2. 50 布局扫描是单 seed，且数值被标注为 estimate。
  3. 五布局 shot 对照的 population 很小（每任务五个布局）。
  4. 示范选择没有被拆开：三条轨迹由官方 TRAIN 划分预先固定，挑选时不接触测试布局结果，但仍是人工挑选，也没有做 selection ablation——换一批示范会怎样，没有对照。
  5. 示范可能携带强 task prior（成功轨迹加上目标布局），没有与非执行式提示对照。
  6. execution-grounding 与普通 visual prompting 的增益没有被拆开。
  7. anchor memory 没有做 ablation（项目页自述）。
  8. 模型能力档位没有被隔离：没有与更弱模型做同协议对照。
  9. 没有跨本体实验证据，跨本体只出现在讨论中。
  10. cross-task ICL 没有被当前实验直接证明——本文中这类主张只到 L2–3。
  11. Fill Pen Holder 的换手案例在 step 802 因服务故障中断，没有官方结果，只能写成机制观察。
  12. 不同子评测使用不同协议：RoboDojo 官方报告、RoboICL 项目页的 50-layout 图、以及另一份作者方技术报告（GPT-as-Policy）的评测，各自协议不同，数字不得直接横比。

十一、青稞技术小结

RoboICL 值得关注的地方不是某个分数，而是它把 demonstration 从静态样本改成了 execution-grounded context，并且把动作接口、记忆策略和反馈回路一起当作推理时的设计问题来处理。

这套做法留下的可迁移经验并不复杂。接口形状决定了信息粒度：把动作写成固定的 15×14 矩阵、把回执写成一组明确的执行字段，模型才可能从反馈里读出「哪一步没做」——这一点在只把轨迹塞进 prompt 的方案里是拿不到的。省略必须显式：<TRAJECTORY_GAP> 这类标记不是格式细节，而是记忆设计的一部分，它决定了模型会不会把两段不相邻的历史读成连续运动。还有一条来自对比本身：同一个任务在不同协议下的数值可以差出数倍，所以数字和口径必须一起写。

悬念仍然在因果上。示范数、示范与评测布局的关系、基座模型的能力档位、记忆策略，目前都还耦在一起；作者也没有声称解决了泛化问题。把它读成「一种把学习搬到推理时的接口探索」是合适的，读成「机器人泛化已经解决」就超出了现有证据。

所以这篇文章真正想留下的问题不是 RoboICL 拿了多少分，而是一个更基础的问题：学习究竟应该发生在参数里，还是也可以发生在上下文里？ 如果后一条路走得通，那么「部署时给什么上下文」会像今天的「用哪批数据微调」一样，成为工程上必须回答的问题；如果走不通，参数路径的边界也会因此被划得更清楚。

按本文的读法，RoboICL 是这条问题上的一种 inference-time adaptation interface，而不是新的 VLA 代际。它比的是接口，不是模型排行。

附：与第二篇《VLA 是怎么成为具身智能主线的？》的关系

第二篇讨论的是 action interface：动作怎么表示、怎么生成、为什么成了 VLA 的核心问题；第三篇讨论的是 adaptation interface：适配发生在参数里还是上下文里。二者是同一技术空间里的不同问题，不是「VLA → RoboICL」的下一代替代关系。
