Agent 需不需要先预测「做完之后会怎样」？——文本世界模型（TWM）技术解读

开场：一次「每一步都没做错」的失败

一个 coding agent 被要求修一个 bug。它读了报错、定位到函数、改了两行、跑通单元测试、提交。整套动作都合规，但流水线在集成测试阶段挂了——它改动的那两行，把另一个模块的隐式假设破坏了。

一个网页 agent 被要求订一张票。它点了搜索、翻了列表、点了「继续」。每一步都对应页面上真实存在的按钮，但它对「点了之后页面会变成什么」没有任何预期，于是在一个需要先选择乘客的页面上重复点「继续」，直到超时。

这两个失败有同一个形状：agent 对「环境在自己动作之后会变成什么样」没有显式的预期。 它不是不会做事，而是不知道做完之后世界长什么样。

2026 年 6 月的一篇综述把这类问题收拢成了一个研究对象——text world model（TWM，文本世界模型）。它的定义只有一行：给定当前状态和候选动作，预测后继状态的文本呈现。网页、终端输出、API 响应，甚至用户的下一条回复，都算「后继状态」。

这篇综述值得单独解读，不是因为它提出了新模型，而是因为它把散在四个领域里的做法收进了同一个坐标系，并且顺手把一个更本质的问题摆到了台面上：一旦把「世界会怎样」变成显式变量，最先卡住的不是建模能力，而是判据——在文本世界里，什么算「预测对了」？

一、Agent 的主流形态是反应式的

综述开场的判断很直白：LLM agent 已经在浏览网页、编辑代码、编排工具、和用户长对话，但多数仍然是反应式的（reactive）——每一步把当前观测映射成下一个动作，对「环境如何结构化地演化」没有显式、可检查的模型。

它把 agent 面对的文本环境分成四类，这四类的动力学各不相同：

环境动力学由什么决定典型的「后继状态」
网页前端状态机与后端接口下一页的 DOM / 无障碍树
代码与终端语言与运行时的语义编译输出、日志、退出码
工具与 API服务契约结构化响应或错误
人（对话）人的偏好、意图与任务进度用户的下一条回复

四类的共同点是：界面是文本。 这条约束看起来只是工程细节，但它决定了这个世界模型该怎么做、怎么评——下一节会看到，它带来的三个特性，正是像素世界模型那套框架搬不过来的原因。

值得注意的是「反应式」不是贬义。在分布内，反应式策略往往是最稳、最省的一档：不需要额外推理，不需要维护状态，一次前向出动作。问题只在当正确性取决于动作之后的演化时，这条接口里没有位置放「后果」。

二、为什么不能把像素世界那套搬过来

世界模型不是新东西。强化学习里的 model-based 方法早就在做「预测下一个状态」，具身侧的 WAM（world-action model）也在把未来观测拉进控制回路。既然都是世界模型，文本世界能不能直接套用那套分类与评测？

综述的答案是：不能，并给出三个在像素或状态向量世界里不存在的张力。

第一，状态是开放词表且歧义的。 同一个网页状态可以有无数种合法描述，哪一种是「正确」的没有一个可枚举的答案。像素世界至少还有一个像素级真值，文本世界连真值的形式都要先约定。

第二，动力学是知识承载的。 一个转移是否合理，常常取决于关于这个世界的背景事实，而不是文本表面。删掉一行配置会让服务起不来，这个因果关系不在文本里，在系统知识里。

第三，正确性是语义的、主观的。 很少存在唯一的正确答案。一段输出可以措辞完全不同却语义等价，也可以措辞几乎相同却错得离谱——判据本身成了研究对象。

把三条张力落到具体场景会更清楚。歧义：同一个页面在无障碍树里是几百个节点，在截图里是一张图，在 HTML 里是几万字符——三者的「同一个状态」需要先约定。知识承载：预测「删掉这一行配置会怎样」，靠的不是文本模式，而是对这套服务如何启动的理解。语义正确性：一段终端输出用不同措辞复述可以完全等价，而一个字符之差可能意味着构建失败。三条张力各自都在说同一件事：这里的「对」需要被定义，而不能被默认。

这三条合起来解释了本文后半部分的主线：能力问题之外，还有一个判据问题。 这也是我认为这篇综述最值得读的理由——它没有停在「我们也能做世界模型」这一层，而是把「怎么算做对了」当成一等公民来处理。

三、TWM 到底是什么：一个反事实的转移函数

综述把 TWM 定义在转移函数这一层：

M : S × A → TS    ŝt+1 = M(st, at)

其中 S 是 agent 可见的状态，A 是候选动作，输出 ŝt+1 是后继状态的文本呈现——可以是一段自然语言描述、一条结构化记录、一段代码，任何能说明「执行 at 之后什么成立」的东西。

这个定义有两个刻意的留白，读的时候容易滑过去：

留白一：输入状态不必是文本。 「文本」限定的是转移被暴露给 agent 的形式。输入可以是对话历史、终端轨迹，甚至是网页截图。

留白二：底层载体不受限。 一个 TWM 可以用提示从冻结的 LLM 里「问」出来，可以训练成一个专用的转移预测器，也可以直接写成可执行的程序逻辑。

真正把它和相邻概念区分开的是反事实性。普通的 LLM 回答是「这样说对不对」，TWM 回答的是「如果这么做，交互状态会怎么变」。前者是对当前信息的应答，后者是对一个未发生的动作的推演。综述在这一点上划了两条界线：

  • 与经典隐空间世界模型相比，TWM 把动力学摊开成可以阅读、编辑、验证、并回喂给 agent 的文本；
  • 与普通 LLM 回答相比，TWM 的角色是明确的反事实，而不是被动应答。

范围上，综述覆盖两个交互对象：外部环境（网页、代码仓库、工具 API）与人类用户（偏好、意图、任务进度的演化）。后者平时容易被归到「对话系统」里，这篇综述把它和网页 / 代码放在同一层，理由是两者在数学形状上是同一个东西——都是「状态 + 动作 → 后继状态」。

综述最有用的产出是一张分类图，用两个轴把现有工作摊开：

轴一，状态表示（从灵活到形式化）：自然语言 → 结构化（JSON、知识图谱、无障碍树、PDDL 谓词）→ 可执行代码。

状态表示特点代价
自然语言LLM 最容易生成与消费一致性、完备性、可执行性都弱约束
结构化实体、关系、前置条件与效果显式可查需要 schema，覆盖面受限

轴二，grounding domain（模拟的是哪一种世界）：

  1. 物理——具身环境、游戏物理、灾害场景，有效性依赖常识或模拟物理；
  2. 数字——网站、操作系统、代码仓库、终端、工具 API、GUI，有效性由已部署的系统决定；
  3. 社会——话语、偏好、情绪、协作与任务进度；
  4. 抽象——规划域、数学环境、博弈抽象、逻辑谜题，有效性与任何运行时无关。

两轴交叉得到十二个格子，综述把相关文献逐格填了进去。这张图的用处不是好看，而是它让原本分属不同社区的问题可以互相借力：网页转移预测和用户模拟在此之前几乎不共享语言，放进同一张图之后，「怎么判对」和「怎么拿到数据」这两个问题立刻可以横向对照。

需要说明的是，这两个轴是该综述提出的分析框架，不是领域共识。它自己也没有主张格子已经填满——物理与抽象两列明显比数字列稀疏。

五、三条路线，和一条选择规则

世界模型怎么造？综述把做法归成三条paradigm，并把它们排在一条「隐式 ↔ 显式」的谱系上：

路线知识存在哪优势代价
Learning（微调 LLM 成 WM）模型参数里保真度高、压缩好可验证性差、长程一致性弱
Prompting（ICL / RAG / 自演化）上下文与检索库门槛最低、适配最快幻觉、标定差
Programmatic（code-as-WM）可执行的代码 / 环境确定、可复现、可复用逐环境构建，且只适用于可代码化的动力学

图 2：该综述把三条构建路线排在一条「隐式 ↔ 显式」谱系上——越往右，世界知识越是以可检查的产物形式存在（参数 → 提示与检索 → 可执行代码）。来源：Yixia Li et al., arXiv:2606.09032v1, Fig. 6。

三条路线之外，真正有决策价值的是选择规则。综述给的判据是：先问目标动力学能不能写成闭式描述。

  • 能写——游戏规则、工具 API、GUI 状态机——优先用 code-as-WM：确定性与可验证性是白拿的；
  • 不能写，且属于开放长尾——日常常识、网页的长尾行为——只能用 LLM-as-WM；此时再分两岔：能收集到足够轨迹数据就训练，数据稀少就用提示。

在我看来这条规则比分类本身更实用：它把「该选哪条路」从偏好问题变成了对动力学形式的判断。

Prompting 这一支内部还分三小类，选择顺序大致是「先加例子、再加检索、最后让它自己攒知识」： in-context world modeling（把示例与规则写进上下文，让冻结模型扮演环境）、retrieval-augmented world knowledge（把环境事实放进可检索的知识库，缓解上下文有限与知识过期）、以及 self-evolving prompt world models（让模型把每次预测的反馈沉淀回知识库，逐步演化）。三者的共同上限是同一个：没有参数更新，动力学只能靠上下文与检索来约束。

综述还记录了三股趋势：监督信号正在离开 token 级保真（SFT 转向奖励训练）、提示路线正在从冻结先验走向检索与自演化知识库、扩展的对象正从「更多轨迹」变成「更多环境」。最后一点值得记：环境数量与多样性正在成为头等的扩展轴。而「代码层 + LLM 层」的混合方案，被它列为仍然欠探索的方向。

六、要多少数据：从两万到五万亿

这一节的所有数字都来自综述援引的其他工作，不是综述自己的实验——写稿时句式必须保留这一层归属。综述把这些工作排成了一条台阶，用来说明「环境越开放，所需数据量级越大」：

环境类型数据规模归属
封闭、结构化（ALFWorld、SciWorld）约 2 万条轨迹后饱和综述援引 Word2World
开放网页（WebShop）7 万条仍继续提升同上
工具使用（StableToolBench）16 万条仍未饱和同上
真实网页轨迹106 万条 rollout，训练 32B 模型，仅用 0.09% 的 chain-of-thought 数据激活推理综述援引 WebWorld
代码执行轨迹5T token 的 mid-training，得到 32B 模型综述援引 Code World Model

这五档不能横向比较，也不能相加。 口径分别是轨迹数、rollout 数与 token 数，任务分布也完全不同；它们只支持一个方向性结论：环境越开放，饱和点越靠后。

其中最后一条对「能力会不会被规模解决」这个问题最相关。综述援引的工作显示，在足够规模的代码执行轨迹上做继续预训练，模型可以在不依赖实时执行环境的情况下模拟程序执行、预测输出并判断终止。综述由此提出一个类比：世界建模能力可能像其他语言模型能力一样，是随着数据与算力越过阈值而涌现的。

我对此的态度是：它是一份重要提示，但不足以取消判据问题。能力上来了，不等于「哪一次预测算对」这个问题就有了答案——下一节和第十节会分别从训练信号与评测协议两个方向说明为什么。

七、训练期：世界模型扮演三个角色

世界模型训出来干什么？综述把训练期的用法分成三类，每一类回答一个不同的问题：

角色一：内化进参数（internalize）。 让 agent 在训练后保留环境知识，部署时不再需要外部模拟器。这是「把世界模型学进策略里」的路线，代价是世界模型与策略共享容量，两个目标会争夺参数。

角色二：当作训练环境（WM-as-environment）。 当真实环境访问昂贵、缓慢或不安全时，用世界模型替代它。综述进一步区分了三种强度：离线（一次性合成轨迹）→ 在线（训练中按需 rollout）→ 与策略共同演化（co-evolution，世界模型和策略一起更新）。

角色三：用户模拟（user simulation）。 把人的动力学塞进训练回路。真实用户对 RL 来说太随机、太稀疏，所以需要模拟用户来提供交互信号。

图 3：三种训练期范式——① 内化进参数（世界模型与策略共享参数），② 把世界模型当训练环境（想象 rollout 再训练 agent），③ 用世界模型模拟用户做多轮交互。来源：Yixia Li et al., arXiv:2606.09032v1, Fig. 7。

把训练期用法按「世界模型以什么形态出现、需不需要真机 / 真环境」摊开，可以看出这条线的工程权衡：

形态世界模型以什么出现训练时是否需要真实环境
内化（internalized）没有任何外部世界模型，知识在策略参数里需要（要真实数据）
离线环境（offline）外部 LLM 或代码环境一次性合成轨迹不需要
在线环境（online）训练中按需 rollout（模拟器或经验模型）不需要
共同演化（co-evolve）世界模型与策略一起更新部分需要

这张表读出来的结构是：越往「不需要真实环境」的方向走，对世界模型的依赖越重，误差也越容易在闭环里被放大。 而共同演化处在中间——它换来了世界模型的持续修正，代价是训练回路的复杂度与不稳定性都上去了。

综述记录的趋势是：世界模型正在从静态资产变成动态伙伴——离线轨迹在被在线 rollout 取代，并越来越倾向于与策略共同演化；用户建模则正在从「用提示让助手模型扮演用户」转向用人类对话数据训练专门的用户模型。

八、两个反复出现的失败模式

这一节是全文最实用的部分，因为两个失败模式都不挑场景。

失败模式一：sim-to-real gap（训练里会做 ≠ 部署会做）。 综述把它列为最显眼的失败模式，并给出一个具体的、可测量的方向：这个差距在用户模拟上最大。它援引的工作显示，用 assistant LLM 来扮演用户时，模型会表现得过度配合、风格单一，从而系统性地高估被测 agent 的能力；而且这种偏差在不同人群与方言上并不均匀。

这条有两重含义。第一重是训练侧的：用模拟用户训出来的 agent，到了真实用户那里会掉一档。第二重更根本——如果模拟用户本身就是不可信的，那么拿它当评测环境得到的结论也不可信。 这一点在第十节会再出现一次。

失败模式二：coverage drift（覆盖漂移）。 策略一旦走到世界模型没被设计过的状态，模拟输出就开始偏离任何真实环境。前一个模式说的是「模拟得不够真」，这一个说的是「模拟得不够全」。

这两条的共同点值得单独说一句：它们都不是靠把模型换大一号能解决的。 前者依赖「用户到底是怎么反应的」这类分布外知识，后者依赖覆盖面——两者都指向数据与协议设计，而不是参数量。

九、推理期：模拟器与验证器

推理期只有两种用法，综述把它们分得很清楚：

用法一：世界模型作为模拟器（simulator）。 用于前瞻——浅层 lookahead（往前推一两步看结果）或深层树搜索（把候选动作展开成一棵树，用预测状态给节点打分）。它出现在「策略自己产不出可用候选」的场合。

用法二：世界模型作为验证器（verifier）。 用于筛选与修正——单动作门控（这个动作放不放行）、候选排序（几个候选取哪个）、以及由错误触发的重生成（预测显示会出问题，就让策略重写一次）。它出现在「已经有可用候选集」的场合。

图 4：左、中是模拟器的两种深度——浅层 lookahead 只推一步，深层树搜索把候选动作展开成树；右侧是验证器，世界模型预测动作后果，由裁判决定接受还是打回重写。来源：Yixia Li et al., arXiv:2606.09032v1, Fig. 8。

为什么前瞻会把误差放大？因为搜索的每一步都建立在上一步的预测之上——单步误差会在深度上累积，而 agent 往往用「搜索出来的分数」当作信心。综述的表述更克制：两种用法的「触达范围」都被同一个问题限制，即世界模型逼近真实环境的准确程度。这里要补一句：在反应式策略里，错误只发生一次；在带前瞻的回路里，错误会被用来做决策。

两者的分工很清楚，但上限是同一个：都依赖模拟器的保真度。模拟器的预测要么直接决定选哪个动作，要么为验证器的判断提供依据；如果它一开始就偏了，前瞻会把 agent 带向更自信的错误，验证器会拒掉本来正确的动作。综述因此在推理期这一节的结论里把问题原样交回给了评测。

十、评测：从「像不像」到「会不会做出同一个决策」

如果把这篇综述只记一件事，我会选这一节。它把判据的处理方式讲透了。

图 5：该综述把评测组织成三条路线——① 直接比对预测状态与真值（intrinsic），② 把世界模型接进下游任务看表现（extrinsic），③ 把世界模型本身当作评测环境（meta）。来源：Yixia Li et al., arXiv:2606.09032v1, Fig. 9。

第一层判据：字符串匹配。 直接把预测状态和真实状态做字面比较。优点是奖励可以确定性计算、天然防作弊；缺点是分不出「换个说法」和「说错了」。

第二层判据：语义等价。 用冻结的文本编码器，或用 LLM 当裁判，比较语义而非字面。它解决了改写问题，但仍把「预测出来的状态」本身当成比较对象——语义上和真值很接近的状态，仍然可能让 agent 做出完全不同的决策。

第三层判据：行为一致。 不再看状态像不像，而看预测状态是否让 agent 做出与真实状态相同的决策：把一个冻结的参考策略分别放到预测状态与真实状态上，比较它选出的动作。

综述记录了一个让前两层判据同时失效的反例：预测出来的状态在文字与语义上都很接近真值，却丢掉了唯一那个决策关键的 token（例如购物场景里的目标商品）；而一个文字上差得更远、但保住了该 token 的预测，反而让 agent 做对了事。「像」和「有用」在这里分岔了。

这条证据直接支撑我们说「行为级判据更贴近用途」。但它也有明确的限定：行为级信号需要一个冻结的参考策略来评估，这意味着判据本身依赖所选的策略——换一个策略，结论可能变化。综述没有量化这种依赖。

图 6：字符串 → 语义 → 行为三层判据，以及各自失效的位置。这张图是我们把综述在 §3.1.2 与 §6.3 里散着讲的三层判据并到一起画的，不是原论文的图；行为级判据更贴近用途，但它把判据绑定到了一个参考策略上。图：青稞社区绘制。

训练侧的奖励设计，与这里的判据层级是同一件事的两面。综述把「奖励该测什么」归成四类，可以看成判据下沉的四个台阶：

奖励家族测的是什么已知问题
表层保真（surface fidelity）与真实状态的字面匹配分不出等价改写与事实错误
语义等价（semantic equivalence）冻结编码器的相似度，或 LLM 当裁判语义接近仍可能导向不同决策
行为一致（behavioral consistency）是否让参考策略做出同一决策依赖所选的冻结参考策略
潜空间一致（latent consistency）隐表示层面的对齐与下游行为的关联尚未系统检验

综述由此给出一个很有洞察的判断：「怎么给世界模型打分」和「怎么训练世界模型」正在沿同一条轴收敛。 训练奖励从 token 保真往下游后果移动，评测指标从字符串匹配往行为保持移动——两边其实是同一场迁移。

评测的第二个方向是把世界模型当作评测环境：多轮交互、双 actor 决策、模拟用户，这些原本难以评测的场景，可以在世界模型里反复跑。综述对这个方向给了一句很克制的结论：benchmark 的结论，只和产生它的模拟器一样可信。

由此产生一个身份变化：模拟器保真度从「手段」变成了「一等评测目标」。综述援引的证据显示这个差距不小——被当作用户来用的助手 LLM 会系统性高估 agent 能力。换句话说，在文本世界模型这条线上，「先证明裁判合格」是必要的。

十一、它还没有回答什么

综述列出的开放问题里，有四个我认为最值得记：

问题一：世界模型与策略应该绑多紧？ 综述把选择分成三种 regime：同一个 LLM 兼两职、共享骨干 + 角色适配、完全解耦。共享参数省掉了状态语言漂移与部署开销，但世界模型的误差会直接进入策略梯度，两个目标还在暗中争夺容量；完全解耦让组件独立扩展、一个世界模型服务多个策略，但策略必须精确消费世界模型输出的状态形式，词表或粒度的漂移会静默地劣化 rollout。

这条判断最有价值的推论是：报「世界模型精度」的论文与报「下游 agent reward」的论文，即使在同一 benchmark 上，也不是在测同一个对象。 交叉读这两类结果时，这一点必须记住。

问题二：世界模型本质上是推理任务。 多数 TWM 做的是直接的下一个状态预测，但预测代码执行要追控制流，模拟科学实验要对因果推理，用户建模要推断潜在意图。综述指出现有训练方式（轨迹级 SFT）鼓励的是表层模式匹配而不是推理，并列出三条欠探索路径：从更强的老师蒸馏思维链、把推理目标与预测目标联合训练、以及用过程奖励的 RL。

问题三：agent 架构不会用世界模型。 综述援引的工作显示，有些 agent 在不到 1% 的 episode 中真的调用了世界模型。它的判断是：现有 agent 架构不是照着世界模型的能力设计的。未来的架构需要显式回答三件事——什么时候查询、信任到什么程度、预测错了怎么纠正。

问题四：落地到物理世界与持续学习。 多数 TWM 只活在数字环境里；把文本预测接到传感器、物理约束与真实后果上仍属早期。另一边，真实环境是非平稳的——网站会改版、API 会变、用户偏好会漂移——长期持续学习（既要适应新环境，又不能丢掉老环境）目前还没有成体系的方案。

问题五：地图本身还不平衡。 回到第四节的两轴坐标，综述填进格子里的工作密集分布在数字这一列，物理与抽象两列明显稀疏，社会一列则高度集中在一件事上——用户模拟。这不是填表不勤，而是这三个方向的动力学更难形式化：物理需要常识与传感器，抽象需要形式化规则，社会需要关于人的分布外知识。

图 7：该综述的生命周期图——世界模型先被构建（§3），再用来训练 agent（§4），在推理期给出前瞻（§5），最后被评测（§6）；虚线是「用评测结果反过来改进世界模型」的回环。来源：Yixia Li et al., arXiv:2606.09032v1, Fig. 2。

图 8：世界模型与策略的三种耦合方式——同一模型兼两职、共享骨干与角色适配、完全解耦。三种方式下「世界模型精度」与「agent 收益」不是同一个测量对象。三种方式的划分出自该综述 §7.1；卡片中的取舍与「适合」为我们的整理，图由青稞社区绘制。

十二、青稞技术小结

把这篇综述放回它自己的坐标系，我想可以留下三条判断：

第一，它最实的东西是把四个领域收进同一张地图。 网页、代码、工具、对话此前各自为战；两个轴（状态表示 × grounding domain）加上生命周期四段（构建 / 训练期 / 推理期 / 评测），提供了一个可以横向对照的语言。

第二，它最有信息量的判断是「判据先于能力成为瓶颈」。 三层判据的演进、以及「语义接近但决策不同」的反例，都指向同一件事：在文本世界里，难点不在把未来写出来，而在定义什么叫写对了。 这条判断有保质期——综述自己援引的规模化结果显示建模能力仍在快速变化。

第三，它对具身侧的读者是镜像而非平移。 具身世界模型预测的是像素或潜状态，判据的难点在「像不像」与「做不做得到」之间；文本世界模型预测的是文本状态，难点在「像不像」与「会不会做出同一个决策」之间。两者形状相同，代价与失败模式不同——「行为级判据优于表层相似」这一条在两边都成立，这是可以互相借用的部分；而数据规模、成本口径与用户建模的具体结论不能直接搬。
