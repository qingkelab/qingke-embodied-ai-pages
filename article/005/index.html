给 VLA 套一层 agent harness，能补上哪些泛化缺口？——RPent 与 Harness VLA 技术解读

开场：动作对了，但对着错的东西

机械臂把红色积木夹起来，移向盒子上方，姿态、速度、夹持力都符合示范的样子。松手之后积木落在盒外——因为这一轮的目标标记被换到了另一个盒子上，而模型仍然按上一轮的绑定执行。

这类失败和「抓不住」不是一回事。抓取动作本身没有问题，问题出在动作所对准的目标、所在的空间布局、或者所处的任务阶段。2025 年 10 月提出的 LIBERO-PRO 评测专门构造这类扰动，用来检查模型是在完成任务，还是在重复记忆里的轨迹。

Harness VLA 这篇 2026 年 7 月的论文用一个数字说明这个缺口有多大：同一条 VLA，即 RLinf 版本的 π 模型（下称 π_RLinf），在标准 LIBERO 上成功率 95.3%，到了 LIBERO-PRO 的扰动设置下掉到 50.0%。

这篇文章要回答的是一个比「怎么把 VLA 训得更好」更窄的问题：当一个模型的动作能力已经足够，失败发生在动作被组织的方式上时，系统里应该多出哪一层？

要回答它，我们需要先看清楚标准接口的假设、扰动型评测暴露了哪几类失败，再来看一个把「谁决定下一步做什么」单独拎出来的系统——RPent，以及它上线的第一项工作 Harness VLA。

一、过去怎么做：把泛化写进参数

要看清 RPent 改了什么，先把主流做法的接口写准确。端到端 VLA 的接口是「看当前观测与指令，输出接下来一段动作」：视觉、语言条件与动作学习在同一个训练框架里联合优化，模型从像素一路算到电机指令。

这条路线在过去三年很成功，它的假设也很清楚：只要训练数据覆盖到足够多的任务、物体、场景与本体，模型在部署时就能泛化。 泛化的来源是数据分布，实现方式是参数。

于是改进的方向自然集中在训练侧——扩大数据规模、混合更多本体、调整后训练配方。这套逻辑在分布内是有效的，也是 2024 到 2026 年 VLA 主线的主要故事。

写成公式会更清楚。按 π 系列论文的形式化，VLA 在历史观测与语言指令的条件下直接预测未来一段动作序列，动作以 chunk 的形式输出：一次想一段、执行一段。等号左边只有动作，没有别的输出。

这条接口的效率来自它的单一性：感知、语言与控制在同一次前向里完成。边界条件也来自同一处——数据分布能覆盖「哪些动作是对的」，却不好覆盖「这一次该把动作对准什么」。 目标绑定、空间布局与任务阶段属于部署时才知道的信息，而端到端策略只能在训练时把它们压进参数的统计里。

一个常见的反驳是「那就把扰动也放进训练数据」。这条路在原理上成立，代价是要为每一种扰动重新采集与训练，而扰动在部署现场是一个开放集合。本文讨论的工作选了另一条路：不动参数，改执行组织。

二、摩擦在哪：三类失败都不在动作层

按论文与官方文档的描述，部署期扰动可以归成三类，它们的共同点是：动作层面看不出来，结果层面才暴露。

第一类是语义重绑定失败。指令里的目标被替换或被重新描述之后，模型仍然按训练分布里最常见的那个目标执行。它能抓住杯子，但抓住的是上一个杯子。

第二类是长时程阶段错位。一个需要十几步的任务里，模型在错误的阶段做了局部合理的动作——比如在还没摆好位姿时就开始放置。单看每一步都像是对的，串起来就不成立。

第三类是局部接触不稳定。不规则物体的抓取、受限空间的放置、抽屉与门这类铰接机构的交互，对接触点与力方向敏感，稍微偏移就失败，而且失败之后很难靠同一动作重试救回来。

评测侧对第一类问题的警觉有明确来源。2025 年 10 月提交的 LIBERO-PRO 把关注点写进了标题（Beyond Memorization）：如果模型在标准 suite 上分数很高、在目标与布局被替换后失效，那么高分反映的是对训练轨迹的复述，而不是任务能力。这个评测出现的意义在于，它把「扰动」从一种工程意外变成了一个可测量的维度，也让「加一层 harness 有没有用」有了可比的对照面。

图 3：三类失败的共同点是动作层面看不出来、结果层面才暴露。图中不包含任何成功率或排名，只标出每类失败各自的介入点：planner 按当前观测重绑定目标、检查执行反馈后再分段、先摆位再让 VLA 定向重试。图：青稞社区绘制，编辑部解释框架。

把三类放在一起看，会发现它们不是「模型不够强」的同一种表现。第一类和第二类本质上需要「重新确认一次现在是什么情况」，第三类需要「换一个初始条件再试一次」。而标准 VLA 接口 观测 + 指令 → 动作 里，没有给这两件事留位置。

编辑部判断：这也是为什么单纯把 VLA 做得更大，不一定会解决这三类失败——它们缺的不是局部动作能力，而是动作之间的组织与判断。这个判断只在本文讨论的扰动型评测设定下成立，不等价于「扩大数据规模没有用」。

三、新工作改哪一层：把 VLA 降级成一个可重试的工具

Harness VLA 的核心动作只有一句话：把冻结的 VLA 变成一个可以被反复调用、也可以被放弃重试的接触密集操作原语，把「这一步该做什么」交给一个 agent 形式的 planner。

论文与官方文档反复强调两条约束：全程不更新 VLA 的权重，也不在部署期扩张原语库。改动全部发生在执行组织层：

「不扩张原语库」这条约束比它看上去更严格。它的意思是：遇到新任务时，不允许临时加一个专用工具把事情绕过去，只能调整已有工具的调用顺序、参数与重试策略。这样一来，系统展示的就是现有能力被组织之后的上限，而不是新写一个工具的效果。

原先由谁负责现在由谁负责
端到端策略同时负责语义理解与全部动作planner 负责语义重绑定、分段与重试；VLA 只负责接触密集阶段
失败即 episode 结束或重新采样失败后 planner 从最新 RGB-D 观测判断结果，必要时重新摆位再定向重试
泛化靠训练分布覆盖泛化靠「这些原语在什么条件下可靠」被写成记忆，并在部署时按当前观测重新绑定参数

第二行的「重新摆位」值得单独说。传统重试是把同一个动作再执行一遍，但接触类失败往往是因为初始状态不好；先做一次非接触的位姿调整，再让 VLA 出手，成功率会明显不同。这个动作在接口上是 planner 的调度决策，不是 VLA 的能力。

「工具」在这里不是比喻。按官方文档的系统描述，VLA 原语与脚本化工具注册在同一张工具表上，每个工具都有名字、描述与参数 schema，调用后必须返回结构化结果，planner 看到的是一份统一的调用清单，不需要知道背后是神经网络还是几何计算。这个「不区分」正是降级的含义：VLA 的输出不再直接驱动控制循环，而是成为 planner 的一次可供评估、也可以被放弃的尝试。

代价也随之出现。一次 VLA 调用变成一次完整的工具调用，中间多了判断、序列化与失败分类；这部分开销在第八节有具体量级。

编辑部判断：这条路线最容易被误读成「用 LLM 做任务规划」——那是更早就有的一类思路。本文更愿意把它看成两件事的组合：一是接口改动（VLA 从策略降级为工具），二是工程资产的沉淀方式（把「什么条件下这个工具可靠」写成可复用的记忆）。后一件是这套系统新增的部分。

四、系统结构：三个进程与一张工具表

RPent 把一次运行拆成三个角色，各有明确边界：

Agentic Planner 是一个 coding agent 形式的规划器，负责解释任务、读 RGB-D 观测、重绑定目标与区域、检查执行反馈、选择与排序原语。它看到的不只是任务描述，还包括上一次工具调用返回的文本与图像。

Action Primitives 是原语层。VLA 以 pi0_pick、pi0_doubled 这样的名字进入工具表，与 move_to、rotate_wrist、back_project 这类脚本化工具并列。planner 看到的是一张统一的工具表，不需要知道哪个工具背后是神经网络、哪个是几何计算。

环境与 VLA 服务 是两个独立进程。仿真器作为 env_server 通过轻量 RPC 与 agent 通信，agent 侧不 import 任何仿真器；VLA 侧同理走 vla_server。这样换仿真器只需要实现同一套客户端接口。

一次运行的循环是五步：planner 推理并调用工具 → 原语向 vla_server 请求动作 → env_server 执行 → 返回新观测与相机帧 → 组装成文本与图像上下文回到 planner。循环在 planner 调用 finish（success / failure / stuck）或触及步数上限时结束。

还有一个设计值得单独记下来：planner 是可替换件。 用 --planner 可以在 RPent 自带的 api（基于 pydantic-ai 的工具调用循环）、claude_code（复用 Claude Agent SDK 运行时）、codex（复用 Codex SDK 运行时）之间切换，而工具与提示词保持不变。官方文档给出的理由是：三者面对完全相同的工具集，因此可以在同一个物理 benchmark 上直接比较 planner 本身。

进程隔离这一层带来的是工程收益：仿真环境可以单独重启、搬到另一台机器、或者整体替换，而不需要动 planner 与工具。它对技术结论没有直接影响，但它解释了同一个 harness 为什么能在 LIBERO、RoboCasa、RoboTwin 与真机之间切换——换环境只需要实现同一套客户端接口，判断逻辑不用重写。

图 1：端到端 VLA 把「理解」与「执行」放在同一次前向里；harness 把理解、分段与重试提到 planner，VLA 退回成一个可调用的接触密集原语。图：青稞社区绘制。

五、核心机制：两类原语与两类记忆

原语层按「是否需要接触」分工，这是整套设计的骨架。

解析原语（Analytic Primitives） 是一小组固定不动的手写能力，处理非接触操作：摆位、空间运输、位姿调整、夹爪控制、导航与释放。它们可解释、可复现，失败原因通常看得懂。

VLA 原语 只有一个，就是那个被冻结的 VLA，负责接触密集操作：不规则物体抓取、受限空间放置、按钮按压、抽屉与门的交互。它每次执行完，planner 都要从最新观测判断结果，必要时调整状态再来一次。

这个分工的含义是：把「容易出错且难以解释」的部分压缩到尽可能小的范围里，其余部分交给可验证的规则。 VLA 不再是万能策略，而是一个有明确适用条件的高价值工具。

记忆分两类，解决的是不同尺度的问题：

Task-Specific Memory 记录同一任务上验证过的执行策略，并把它蒸馏成参数化的原语组合。部署时 planner 按当前观测重新绑定目标与空间参数，于是同一条策略能适配被换掉的目标或改动的布局。

Global Memory 记录跨任务的成功模式、失败模式与恢复策略——哪些情形下应该先摆位再让 VLA 出手，哪些失败值得重试、哪些应该放弃。

记忆的组织方式也写进了实现里：目录分 global/、suite/、task_only/ 三层，评估阶段只读，探索阶段可写。官方文档还说明探索模式目前仅在 LIBERO 上支持，且记忆数据集 RLinf/RPent-memory 是公开的 Hugging Face 数据集，无 token 也能下载。

从探索到部署的路径可以概括成三步：从单个种子任务出发，发现解析原语与 VLA 之间有效的分工；把成功的执行策略与恢复经验蒸馏进两类记忆；部署时用记忆加实时观测重新绑定参数。参数在 VLA 里不动，能动的部分被放进了记忆和执行顺序里。

「只读 / 可写」这条边界值得多看一眼。它意味着评估阶段看到的记忆是一份冻结资产：同一任务上多次运行不会互相污染，也不会出现「跑得越久越准」的改进。反过来说，探索阶段的质量决定了部署阶段的上限——记忆写得差，部署时的参数重绑定就是在放大错误。官方把记忆上传做成 maintainer 审核制，也说明他们把记忆当资产而不是缓存来管理。

图 2：planner 面对一张统一的工具表，工具表背后是解析原语与冻结 VLA 两类实现；两类记忆分别支撑任务内参数重绑定与跨任务策略选择。图：青稞社区绘制。

六、实验结果：分布内几乎不变，扰动下变了三十多个百分点

官方文档给出的代表性结果如下，四组数字都来自仿真环境：

LIBERO-PRO扰动桌面操作82.4%π_RLinf 50.0%、RATS 43.8%、Cap-X 18.2%

RoboTwin C2Rclean→randomized 双臂58.4%LingBot-VLA 50.4%

最值得注意的一行是前两行的对比。在标准 LIBERO 上，96.0% 对 95.3%，几乎没有区别；换到 LIBERO-PRO，82.4% 对 50.0%，差距变成 32.4 个百分点。

这说明收益不是「模型变强了」，而是「在目标绑定与空间布局被改动时不再掉线」。如果只看标准 suite，很容易得出「加一层 harness 没什么用」的结论；如果只看扰动评测，又容易高估它的能力。两个数字要放在一起读。

读这四组数字时还需要做三次口径对齐。其一，每一行的对照方法都与它写在同一张表里，跨表不并列；其二，harness 侧调用的是各自环境的 VLA 原语（LIBERO 侧 π_RLinf、RoboCasa 侧 RLDX-1、RoboTwin 侧 LingBot-VLA），所以每行的提升都是相对「同环境的 VLA 基线」，不是相对某个统一模型；其三，官方文档没有给出这些结果的随机种子与独立运行次数，重复性目前只能依赖仓库中为复现准备的环境分支。

论文摘要在总结提升幅度时用了另一个口径：相对最强相关基线，LIBERO-Pro 提升 38.6 个百分点、RoboCasa365 提升 25.4 个百分点，并在 RoboTwin C2R 达到 58.4%。 后一个数字可以直接对上（55.4% − 30.0% = 25.4），但前一个需要读者自己反推——82.4% 减 38.6 得到 43.8%，也就是 RATS 的分数，而不是同一张表里更高的 π_RLinf（50.0%）。

编辑部指出的口径问题：摘要没有逐条点名这条基线是谁，而按官方文档的表格，同环境上 π_RLinf 的 50.0% 高于 RATS 的 43.8%。以不同基线计算，提升幅度会分别是 38.6 与 32.4 个百分点。这很可能是把同项目 VLA 视为对照条件而非竞争方法所致，但一手来源没有写明理由。本文的处理方式是两个数字都写、都保留来源，不替论文选基线。

官方文档把增益归为三条机制：planner 的语义重绑定、重新摆位之后稀疏而定向的 VLA 重试、以及用解析原语隔离非接触执行。这三条都是机制描述，论文没有给出逐项的独立消融。

七、2026 年 9 月的官方榜单：同一个 harness，换 planner 差十个点

2026 年 9 月，官方上线了一个交互式排行榜，覆盖 LIBERO-PRO、LIBERO、RoboCasa365 Target50 与 RoboTwin 四组环境，并把「同一个 harness 换不同 planner 与模型」直接做成了可比较的行。LIBERO-PRO 上排在最前的几行是：

Claude Code / Opus-4.7 / max.reasoning82.4%

Codex / GPT-5.5 / xhigh / reasoning72.1%

π_RLinf（不带 harness）50.0%

两个观察：

第一，harness 的收益里，planner 与模型本身贡献很大。同样是不更新 VLA、不扩张原语库，换 planner 就能从 72% 走到 92.63%。所以「不训练模型」不等于「不依赖模型能力」——这条路线把能力需求从动作模型转移到了推理模型。

第二，论文里的 82.4% 对应的是 Opus-4.7 这一行。论文 v1 在 2026 年 7 月发布，榜单在 9 月更新；引用 92.63% 时不能写成论文成绩，引用 82.4% 时也要说清它对应的 planner 配置。这是本文在引用时逐行标注配置的原因。

把 planner 做成可替换件，还有一个容易被低估的作用：它让「推理模型的能力」变成可以单独测量的变量。 在这套框架里，工具、原语、记忆结构都固定，唯一变化的是驱动工具调用的那个模型与推理档位——LIBERO-PRO 上从 70.63%（Qwen3.6 27B，非推理）到 92.63%（GPT-6 Astra，低档推理）的跨度，基本可以读成 planner 侧能力的贡献区间。对做具身系统的团队来说，这个对照比多涨几个点更有参考价值：它说明在这一层上投入推理模型是有回报的，而且是可替换、可升级的回报。

引用 92.63% 还必须同时带上官方页面自己给出的两条限定：

限定一，这个数字由两批不重叠的回合合并而成。 页面写明：Long Task / Long Swap 与其余六个 suite 使用各自探索阶段结束后冻结的记忆文件快照，评估期间不再更新；总分由 Long 的 157/200 加上其余 suite 的 584/600 构成 741/800。页面特意强调，这 800 个回合不共享同一份记忆快照。

限定二，榜单由被评测方维护。 页面自己声明这些结果只适用于所展示的方法与评测覆盖范围；各方法在不同配置下自报成绩，任务集、基线与本体并不统一。因此这份榜单适合用来读「同一个系统内部不同档位的差异」，不适合用来给跨方法的能力排序。

RoboTwinRPent / GPT-6 Astra1,078.8 秒2,763,641

把这些数字换算成直观的量级：LIBERO-PRO 上每个回合平均要跑将近七分钟、消耗三百多万个输出 token；RoboCasa365 上平均每回合接近二十分钟。

同一页面上还有一行很说明问题的数据：Flash Mode 用 Molmo2-8B 做视觉定位，每回合 60.19 秒、token 计数为 0，成功率 72.63%。这条线上「成功率」和「开销」是一组可以调档的取舍，而不是单一最优解。 从 72.63% 到 92.63% 的这 20 个百分点，代价是每回合从一分钟变成七分钟、并引入百万级 token 消耗。

README 还记录了一条工程侧的更新：2026 年 8 月加入非推理模式，官方称平均执行时间降低约 40%（未给出测量口径）。这说明这条线自己也在往成本方向优化，只是目前的公开数字仍停留在分钟量级。

编辑部判断： 这类开销在离线评测里可以接受，在连续运行的部署场景里则是硬约束。本文把成本单列一节，是因为它比成功率更容易在讨论中被略过；但也要说清——排行榜没有公布时延的测量口径（是否含服务冷启动、模型下载等），因此这些数字只能作为量级参考。

这里还有一处需要读者自己补上的空白：官方没有给出耗时的分解。 一个 412 秒的回合里，多少花在模型推理、多少花在仿真步进、多少花在图片编码与传输，决定了优化应该往哪一层做。非推理模式能省掉约 40% 的说法，从侧面说明推理环节占了相当比例，但具体结构仍然不明。对准备复现这套系统的人来说，这比成功率更影响可行性判断。

九、与相邻路线比较

把这条线放进 2026 年具身智能的几个接口里横向读：

工作它改的是哪一层是否更新参数主要解决的问题
端到端 VLA（π0.5、RLDX-1、LingBot-VLA）策略本身：观测与指令直接映射到动作训练时更新分布内的动作能力与泛化
RoboICL 一类部署期适配示范如何进入决策的上下文接口否部署现场的行为调整
WAM（World-Action Models）决策是否显式包含动作后果训练时更新动作之后的物理演化
RPent / Harness VLA执行由谁组织：谁决定这一步做什么否（VLA 冻结，记忆与调度变化）目标重绑定、阶段错位、接触失败后的重试

四者不是替代关系。RPent 的 README 已经把 WAM 侧的 DreamZero 列为待接入的 Action Primitive，说明这几条线在工程上是可以组合的：harness 决定「什么时候调用什么」，被调用的模型决定「那一步怎么做」。

与 RoboICL 的对比更能说明这一层的独立性：两者都不更新参数、都在部署期解决问题，但 RoboICL 改的是「示范以什么形式进入上下文」，RPent 改的是「有哪些工具、以及它们如何被组织和重试」。前者是上下文接口，后者是执行组织接口。

把四个接口画在同一张图上，可以看到它们问的是四个不同的问题：动作怎么产生、适配在哪里发生、后果是否进入决策、执行由谁来组织。这四个问题各自都能独立推进，也都能被同一个系统同时采用——README 把世界模型列为待接入的原语，就是这个意思。

图 4：横轴是四个接口各自回答的问题，不是能力高低或方法优劣。四者可以并存：harness 决定调用顺序，VLA 决定那一步怎么做，WAM 决定是否考虑后果，部署期适配决定示范以什么形式进入上下文。图：青稞社区绘制，编辑部解释框架。

十、它还没有回答什么

第一，真机证据还是空的。 README 记录 2026 年 9 月才加入 Franka 与双臂 Franka 支持，官方文档与排行榜给出的全部成功率都来自仿真环境。真机上 planner 的时延、重试成本与安全边界目前没有公开数字。

第二，记忆的独立贡献没有被归因。 排行榜上有一行 Motor Only 配置（直接用末端位姿增量与夹爪指令控制，不调用 VLA、不用原语、不加载记忆），它只在 LIBERO-PRO Long Task 上给出 38.0%，其余列为空。这不足以构成一份记忆消融。

第三，跨 benchmark 不构成横比。 各方法的任务集、基线与配置不同，页面自己也这么声明。本文因此只做同表、同环境内的对照。

第四，RoboCasa365 上论文的 55.4% 与排行榜的 59.20% 之间的差异，官方没有逐条说明，两者对应的配置不同，不能取平均，也不能互相替换。

第五，扰动是否覆盖了这条路线最吃力的地方，还没有答案。 目标重绑定与布局变化正是 planner 擅长的部分；如果扰动主要发生在接触动力学层面，harness 能提供的帮助是否同样显著，目前没有公开对照。

把这五条放在一起，可以得到一个比较务实的读法：这套系统目前能支持的结论是，「执行组织」这一层可以在仿真扰动评测里被有效改造；至于这层改造能不能带进真机与接触层，现有材料还不足以说明。 前者已经足够构成一条值得跟的技术路线，后者才是它能不能进入生产系统的分水岭。

还需要提醒一处容易越界的推论。92.63% 常常被当作「agent harness 比端到端 VLA 强多少」的论据，但榜单上并不存在一个「同一模型、同预算、去掉 harness」的对照行——π_RLinf 的 50.0% 是另一个模型、另一套训练流程下的成绩。跨配置的差距只能说明方向，不能给出归因。

十一、青稞技术小结

把这篇工作压缩成一句话：它把 VLA 从「策略」降级成「工具」，把泛化从参数里搬到了执行组织里。

这个改动的价值不在于让模型变强，而在于它把三类原本混在一起的失败拆开了。语义重绑定与阶段错位交给 planner，接触密集操作留给 VLA，非接触的规则化动作交给解析原语。拆开之后，每一部分的失败原因变得可读，重试也有了明确的入手点。

它同时也给这条路线划出了两条边界。第一条是证据边界：目前的收益全部建立在仿真扰动评测上，真机与接触层的扰动尚未验证，记忆的贡献也没有独立归因。第二条是成本边界：把成功率从 72% 推到 92% 的代价是每回合从一分钟变成七分钟、并引入百万级 token；这个量级离连续部署还有距离。

如果要从这里挑一个值得长期观察的变量，我会选「单位成功率的开销」——因为它决定了这一类 harness 是停留在评测台架上，还是能走进真实系统。成功率会随 planner 迭代继续上涨，但只有成本下降一个量级，这条路线才会从「跑分手段」变成「部署方式」。

最后一句话留给工程视角。这套框架里最不像论文的部分，是它把「可靠的适用条件」当成了需要长期维护的资产：记忆要审核、要版本化、要区分只读与可写。对做部署的团队来说，这可能是比 92.63% 更值得抄走的一个设计决定——模型会换代，工具会增删，但「什么情况下该信这个工具」这件事，永远需要有人维护。

附：与前三篇的关系

第一篇讨论具身智能三阶段与数据、评测、世界模型等线索；第二篇讨论 VLA 主线的 action interface；第三篇讨论 RoboICL 的 adaptation interface；第四篇讨论 WAM 的 prediction / consequence interface。这一篇讨论 harness 的 execution-organization interface：在一次任务里，由谁决定下一步调用什么。

五者不是代际替代关系。动作怎么产生、适配发生在哪、后果如何进入决策、执行由谁组织，这四件事可以分别推进，也会互相借用实现——README 把世界模型列为待接入的原语，就是一个具体例子。
